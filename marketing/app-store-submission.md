# Submitting Marginal to the Mac App Store

A step-by-step guide, written against this repo's actual configuration. Where the
project is already compliant, the step says so — several of the usual hurdles are
already done.

## 0. What's already in place

| Requirement | Status |
|---|---|
| App Sandbox enabled | ✅ `Marginal.entitlements` sets `com.apple.security.app-sandbox` — mandatory for the Mac App Store |
| User file access | ✅ `com.apple.security.files.user-selected.read-write` — correct scope for a document-based editor |
| App icon (all 10 slots) | ✅ `AppIcon.appiconset` with icon-3 |
| `CFBundleIconName` | ✅ in `Info.plist` |
| Category | ✅ `LSApplicationCategoryType` = `public.app-category.productivity` |
| Bundle ID | ✅ `com.jochemberends.marginal` |
| Document types / UTI for `.md` | ✅ declared in `Info.plist` |
| Hardened runtime | ✅ enabled (not required for MAS, required if you also ship a notarized build outside the store) |

## 1. Join the Apple Developer Program

- Enroll at [developer.apple.com/programs](https://developer.apple.com/programs/) (€99/year, personal or organization).
- Sign in to Xcode with that Apple ID: Xcode → Settings → Accounts.

## 2. Add the KE-works team to the project

The team is **KE-works**. A commented `DEVELOPMENT_TEAM` line is already in place in
`project.yml` — the project is generated by XcodeGen, so the team must live there (a
setting made in the Xcode UI is lost on the next `xcodegen generate`).

1. Sign in to Xcode with the KE-works Apple Developer account: Xcode → Settings →
   Accounts. The 10-character team ID appears next to the team name (also at
   [developer.apple.com/account](https://developer.apple.com/account) under
   Membership details).
2. In `project.yml`, uncomment `DEVELOPMENT_TEAM:` and paste the ID.
3. Run `xcodegen generate`.

Keep `CODE_SIGN_STYLE: Automatic` — Xcode will create the Apple Distribution
certificate and provisioning profile at archive time. Note: with an organization
account, your Apple ID needs the **Admin** or **App Manager** role in App Store
Connect to create the app record and submit builds.

## 3. Two Info.plist additions worth making now

```xml
<key>ITSAppUsesNonExemptEncryption</key>
<false/>
```
Marginal uses no custom encryption; this skips the export-compliance questionnaire on
every single upload.

Also bump for release: `MARKETING_VERSION` `0.1.0` → `1.0.0` (the store shows this as
"Version 1.0.0"), and increment `CURRENT_PROJECT_VERSION` on **every** upload — App
Store Connect rejects a build number it has already seen.

## 4. Create the app record in App Store Connect

1. [appstoreconnect.apple.com](https://appstoreconnect.apple.com) → Apps → **+** → New App.
2. Platform **macOS**; Bundle ID `com.jochemberends.marginal` (register it first under
   Certificates, Identifiers & Profiles → Identifiers if it isn't offered).
3. Name: "Marginal" may be taken — have a fallback ready, e.g. "Marginal — Markdown Editor".
   The name on the store does not have to match `CFBundleName`.
4. SKU: any internal string, e.g. `marginal-macos`.

## 5. Fill in the metadata

Written in the brand voice (sentence case, short declaratives, no exclamation marks):

- **Subtitle** (30 chars): `Markdown, rendered as you type`
- **Description**: open with the tagline — "Markdown that reads the way it renders." —
  then the feature facts: true WYSIWYG with markers that reveal at the cursor,
  Notion-grade rendering, plain `.md` files that work with git, native AppKit, tabs
  with ⌘1–⌘9, copy as Markdown or HTML, light and dark mode, open source (Apache 2.0).
- **Keywords**: `markdown,editor,wysiwyg,notes,writing,plain text,md,notion`
- **Support URL**: `https://github.com/jberends/marginal`
- **Marketing URL**: the landing page, once hosted.
- **Privacy policy URL**: `https://jberends.github.io/marginal/privacy` — already
  live (states: no data collected, no analytics, no network access; documents never
  leave the Mac).
- **App privacy** questionnaire: "Data not collected" — truthful, and it renders as the
  best possible privacy label.
- **Pricing**: free (paid requires the Paid Applications agreement + banking/tax forms first).

## 6. Screenshots

Mac App Store accepts PNG at exactly **1280×800, 1440×900, 2560×1600 or 2880×1800**.
The marketing renders in `marketing/site/` come from the app's real text engine —
compose them on a paper background at 2880×1800 (`sips -p 1800 2880 …` after padding),
or simply capture the real window on a Retina display with ⌘⇧4 + space. 1–10 images;
the first two matter most: the rendered document (hero), and the table/code view.
Both light and dark variants exist already.

## 7. Archive and upload

In Xcode: select the `Marginal` scheme, destination **Any Mac**, then
**Product → Archive** → Organizer opens → **Distribute App → App Store Connect → Upload**.
Xcode signs with Apple Distribution, embeds the provisioning profile, and validates.

Or from the terminal:

```bash
xcodegen generate
xcodebuild -project Marginal.xcodeproj -scheme Marginal -configuration Release \
  archive -archivePath build/Marginal.xcarchive
xcodebuild -exportArchive -archivePath build/Marginal.xcarchive \
  -exportOptionsPlist exportOptions.plist -exportPath build/export
# exportOptions.plist: {method: app-store-connect, teamID: YOURTEAMID}
xcrun altool --help  # or: upload build/export/Marginal.pkg with Transporter.app
```

The GUI path is genuinely easier for the first submission.

## 8. Submit for review

1. In App Store Connect, the uploaded build appears under TestFlight/Builds after
   ~15 minutes of processing.
2. Attach the build to version 1.0.0, answer the content-rights and advertising-identifier
   questions (no ads, no IDFA), and **Submit for Review**.
3. Mac app review typically takes 1–3 days.

## 9. This app's likely review notes

- **Sandbox behavior**: test the sandboxed build seriously before submitting — open,
  edit, save, save-as, reopen-recent, drag-a-file-onto-the-window. NSDocument handles
  security-scoped bookmarks for recents automatically, but verify.
- **Minimum functionality**: native document-based editor — comfortably clears the
  "not a repackaged website" bar.
- **Open source on the store**: fine — Apache 2.0 permits it and you own the code.
  (GPL apps have historically been pulled; Apache/MIT are unproblematic.)
- **Crash on a clean machine**: create a fresh macOS user account and run the exported
  `.pkg`-installed build once before submitting.

## 10. After approval

- Releases can be manual or automatic; pick manual for the first one so the site,
  GitHub release, and store listing go live together.
- Subsequent updates: bump `CURRENT_PROJECT_VERSION`, archive, upload, submit. Only
  changed metadata needs re-entry.

## Aside: distribution outside the store

The GitHub-releases channel stays useful (users who want no App Store). That build
needs **notarization** instead: archive → Distribute App → Direct Distribution
(Developer ID certificate). Hardened runtime is already enabled, which is exactly what
notarization requires. The same archive can feed both channels.
